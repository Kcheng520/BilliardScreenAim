# 台球屏幕辅助线识别(读屏 + 悬浮窗方案)

识别 **手机屏幕里台球游戏画面** 本身(球桌、母球、瞄准线),而不是用摄像头拍现实球桌,
并把预测的延长瞄准线 + 碰库反弹路径,以悬浮窗形式实时叠加显示在游戏画面最上层。

## ⚠️ 使用前必读
- 绝大多数台球类游戏(尤其带排位/真钱对战的)把"延长辅助线"类工具视为外挂,使用可能导致**封号**。
- 请只在**单机模式 / 练习模式 / 你自己开发调试的游戏**里使用。
- 本方案技术上等同于"读屏 + 悬浮窗"这类工具的通用实现思路,本身不含破解、注入游戏进程等行为,
  也不会修改游戏本体,但仍然建议只用于合规场景。

## 和"摄像头方案"的核心区别
| | 摄像头方案 | 本方案(屏幕方案) |
|---|---|---|
| 输入源 | Camera / CameraX | MediaProjection 截屏 |
| 画面质量 | 有光照、抖动、透视畸变 | 干净、无噪点、无透视畸变(游戏本身就是俯视/固定视角渲染) |
| 识别方式 | 边缘检测 + 霍夫直线为主 | **优先用颜色阈值识别游戏自带的瞄准辅助线**,更准更稳定 |
| 显示方式 | Activity 内的 View 叠加在预览上 | 全局悬浮窗(`TYPE_APPLICATION_OVERLAY`),需要"悬浮窗权限" |
| 权限 | 相机权限 | 悬浮窗权限 + 屏幕录制授权(每次启动都要再次确认) |

## 目录结构
```
BilliardScreenAim/
└── app/src/main/java/com/example/billiardscreen/
    ├── MainActivity.kt          申请权限 + 启动/停止服务
    ├── ScreenCaptureService.kt  前台服务:MediaProjection截屏、节流处理、驱动悬浮窗
    ├── FloatingOverlayView.kt   全局悬浮窗绘制
    ├── BilliardDetector.kt      核心算法(颜色法识别辅助线 + 反弹预测)
    └── DetectionResult.kt       数据结构
```

## 使用流程
1. Android Studio 打开工程,真机运行(截屏需要真实系统权限交互,模拟器也可以但没有实际游戏画面)。
2. App 里点 **"1. 开启悬浮窗权限"**,系统会跳到设置页,给这个 App 开启"显示在其他应用上层"。
3. 点 **"2. 开始屏幕识别"**,系统会弹出"是否允许 XXX 录制屏幕"的确认框,同意。
   - 注意:Android 每次重新启动录屏都要重新弹这个确认框,这是系统限制,做不到静默启动。
4. 切换到台球游戏,悬浮窗会实时把识别结果画在游戏画面上。
5. 想停止时回到本 App 点 **"停止识别"**,或者从通知栏关掉那条"正在分析屏幕画面"的常驻通知对应的服务。

## 算法说明(与摄像头版本的关键差异)

### 优先用"颜色法"找辅助线,而不是霍夫直线检测
`BilliardDetector.detectGuidelineByColor()`:
1. 用 `GUIDE_HSV_LOWER/UPPER` 这个颜色区间把游戏自带的瞄准辅助线抠出来(大多数游戏是白色/浅色虚线);
2. 对抠出来的所有像素点用 `Imgproc.fitLine`(最小二乘)拟合出一条直线;
3. 把这些像素投影到直线方向上,取投影范围两端当作线段端点。

这样比对整张截图做 Canny+霍夫直线稳定得多,因为截屏画面里球杆贴图、UI 按钮、比分板都是很清晰的直线/边缘,
通用边缘检测很容易被这些干扰,误识别成"瞄准线"。**颜色法只要你把辅助线的颜色区间标定准了,基本不会跑偏。**

如果某个游戏根本不显示辅助线(比如你想识别"球杆本身"的指向,而不是游戏画的辅助线),
才会退化用 `detectCueStickByEdges()` 这个边缘检测兜底方案,准确率会明显下降。

### 反弹预测逻辑不变
仍然是"入射角=反射角"的镜面反射,从母球出发沿方向发射射线,和台面四边形边界求交点,
反弹后更新方向,最多算 3 次,细节见 `predictPath()`,原理和摄像头版本完全一样。

## 必须标定的参数(在 BilliardDetector.kt 里)
| 参数 | 说明 |
|---|---|
| `TABLE_HSV_LOWER/UPPER` | 游戏里台呢的颜色区间 |
| `GUIDE_HSV_LOWER/UPPER` | 游戏自带瞄准辅助线的颜色区间(**最关键,直接决定辅助线能不能被找到**) |
| `BALL_SAT_MAX` / `BALL_VAL_MIN` | 母球(通常是白色)的亮度/饱和度阈值 |
| `BALL_MIN_RADIUS/MAX_RADIUS` | 母球在截图里的像素半径,取决于手机分辨率和游戏 UI 缩放 |

**标定建议**:直接在游戏里长按/截图存一张瞄准状态的截图,拖到电脑上用 Python 写几行代码,
鼠标点哪个像素就 `print` 一下它转换到 HSV 后的值(`cv2.cvtColor(img, cv2.COLOR_BGR2HSV)`),
比凭感觉猜阈值快得多也准得多。

## 性能与节流
- `ScreenCaptureService` 里做了节流(`minIntervalMs = 200ms`),避免每一帧都跑 OpenCV 导致发热、掉帧。
  可以按需要调整这个间隔,平衡"实时性"和"耗电/发热"。
- `ImageReader` 用 `acquireLatestImage()` 只处理最新一帧,处理不过来的旧帧会被主动丢弃。

## 已知局限性
- **`FloatingOverlayView` 目前设置为 `FLAG_NOT_TOUCHABLE`**(纯展示,不拦截点击),这样你才能正常操作下面的游戏;
  如果以后想加"手动点击校准台面四角"之类的交互,需要单独做一个可点击的临时校准悬浮窗。
- Android 13+ 上通知需要 `POST_NOTIFICATIONS` 运行时权限,清单里已声明,但 `MainActivity` 里没写请求这个权限的代码,
  实际接入时需要补上(否则前台服务通知在某些机型上可能不显示,但不影响服务本身运行)。
- 不同游戏的 UI 缩放、分辨率适配方式不同,`GUIDE_HSV` 颜色阈值和球半径范围几乎不可能有一套通用参数,
  每换一个游戏基本都要重新标定。
- 部分厂商定制系统(比如 MIUI、ColorOS)对悬浮窗和后台服务有额外限制,可能需要用户手动到设置里给该 App 加"自启动"/"悬浮窗"白名单。
